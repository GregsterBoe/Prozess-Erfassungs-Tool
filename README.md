# Software-Landkarte

A tool for the tax office to map a client's software: which programs, lists and folders
exist, which tasks are done in them, which system leads for each kind of data, how data
moves between systems, the processes behind it, and a target picture for a move to new
software. The UI is German and so are the catalog and modules.

The design lives in the knowledge base as the blueprint `software-landkarte.blueprint`
(`vault/work/projects/software-landkarte/`). This repository is built from it;
`blueprint.lock.yaml` records which version of each blueprint item is built where. The
*why* stays in the blueprint. This file describes only how to use and change the code.

## Use

Open `dist/software-landkarte.html` by double-click. There is nothing to install, no
login, and the page makes no network requests. Its Content-Security-Policy forbids them.

1. **Betrieb**: name the business and choose the industry modules.
2. **Systeme**, **Aufgaben**: add systems from the catalog (their typical tasks come
   along and can be switched off one by one) or create your own.
3. **Daten**, **Flüsse**: fill the matrix (*führt / liest / Kopie*), take over the
   proposed flows, enter the effort per media break.
4. **Prozesse**: check how tasks are assigned and ordered. Tasks with no process are listed
   at the top.
5. **Durchgang**: create the client file (`….mandant.html`) and send it. The client goes
   through the cards and sends back `….durchgang.json`. Read it in here.
6. **Zielbild**: mark the new software, decide per task and per data object, read the
   changeover list. After the move, *Zielbild als neue Ist-Landkarte übernehmen* starts
   the next version of the map from it.
7. **Bericht**: print it, or download it as HTML, the matrix and task list as CSV, and
   the map as JSON (`….landkarte.json`, reopened with *Landkarte öffnen*).

The working state is kept in the browser's local storage. The JSON file is the copy you
keep and pass on.

**Client data never goes into this repository.** Every file the tool writes for a client
matches a pattern in `.gitignore`. The example in `examples/` is invented.

## Layout

| Path | What |
|---|---|
| `src/core.js` | data model and rules, no DOM (browser and Node) |
| `src/report.js` | the report as an HTML string |
| `src/app.js`, `src/index.html`, `src/styles.css` | the UI: office mode and client mode |
| `catalog/software.json` | software catalog: products, typical tasks, data objects, roles |
| `catalog/prozesse.json` | the process core: four standard processes with ordered steps |
| `modules/*.json` | industry modules (Handwerk, Handel, Ladengeschäft) |
| `examples/beispielbetrieb.json` | invented business, 8 systems and 25 tasks; generated by `scripts/beispiel.js` |
| `scripts/build.js` | inlines everything into `dist/software-landkarte.html` and validates the data |
| `dist/software-landkarte.html` | the built tool, committed so it can be used without Node |

## Extending without code

**A new system for the catalog:** add an entry to `catalog/software.json` under
`software`, with `id`, `name`, `kategorie`, `art` (`lokal`, `cloud`, `excel`, `papier`,
`postfach`), `zweck` and `aufgaben`. A task has `id`, `name`, `rolle` (one of `rollen`),
`haeufigkeit` (`taeglich`, `woechentlich`, `monatlich`, `jaehrlich`, `bedarf`),
`liest`/`schreibt` (data object ids) and optionally `schritt` (`process:step`, e.g.
`o2c:rechnung`). The tool uses `schritt` to propose the process. Product names and
typical tasks only: never anything about a client.

**A new industry module:** add `modules/<id>.json`:

```json
{
  "id": "gastro",
  "name": "Gastronomie",
  "beschreibung": "optional",
  "prozesse":    [{ "id": "kueche", "name": "Küche", "schritte": [{ "id": "rezept", "name": "Rezepturen pflegen" }] }],
  "einhaengen":  [{ "prozess": "r2r", "nach": "kasse", "schritte": [{ "id": "trinkgeld", "name": "Trinkgeld verteilen" }] }],
  "ausblenden":  [{ "prozess": "o2c", "schritt": "angebot" }],
  "datenobjekte": [{ "id": "rezepturen", "name": "Rezepturen", "art": "stamm" }],
  "software":    []
}
```

A module can add processes, insert steps after a named core step, hide core steps, and
suggest data objects and software. It cannot rename or delete a core step, and the
validator rejects any other field. When several modules are chosen, a core step is hidden
only if all of them hide it.

Then run `npm run build`. The build refuses invalid data: missing fields, duplicate ids,
unknown references, invalid insertion points, or text that looks like contact data.

## Develop

```bash
npm run build      # dist/software-landkarte.html
npm run example    # regenerate examples/beispielbetrieb.json, then build
npm test           # build, unit tests and browser tests
npm run test:unit  # unit tests only, no browser needed
```

Node 20 or newer. There are no npm dependencies. The browser tests in `test/e2e/` use
Playwright with Chromium (`require('playwright')`). Without Playwright they are skipped.
A test fails when `dist/` is out of date with the sources.

## Checked by hand

Two acceptance criteria need a person, not a test:

- **Browsers** (`software-landkarte.r.lokal`): the automated tests run Chromium. Before a
  release, open the built file and the generated client file once each in current
  Firefox, Safari and Edge. The code uses only standard browser APIs.
- **Walkthrough time** (`software-landkarte.r.durchgangsdauer`): open the example
  (*Beispielbetrieb laden*), create the client file, and let a test person who does not
  know the tool go through all 34 cards. Record the time. The limit is 20 minutes.
